# Codex + Cursor 协作规范

> 本文是本仓库的工程协作流程规范，不代表产品版本号。
>
> 工程结构以 `plan/plan_v1.10.md` 为已落地的计划，产品范围以 [version_outline.md](version_outline.md) 为准；本文规定如何使用 Codex 和 Cursor 安全、可回滚地做后续修改。
>
> 适用范围：`E:\wardrobe` 仓库的 Flutter/Dart、Windows 原生层、数据库、图片处理、ONNX 推理、测试和文档修改。

---

## 1. 核心原则

### 1.1 一个主计划，两个协作角色

- `plan/plan_v1.10.md`：已落地的工程计划。四个阶段不再重开。
- [version_outline.md](version_outline.md)：产品从 v1.1 到 v1.9 做了什么。
- 本文：记录怎么做、谁负责什么、如何审查、如何提交和如何回退。
- Cursor：默认负责连续实现和本地迭代。
- Codex：默认负责任务拆分、架构审查、风险识别、测试设计和必要的定向修复。

不要让两个工具同时自由重构整个仓库。每一阶段必须有一个主要修改者，另一个主要负责审查。

### 1.2 小步、可验证、可回滚

每次修改都应满足：

1. 有明确的目标和文件范围；
2. 不跨越无关模块；
3. 可以独立运行格式化、静态分析或相关测试；
4. 可以通过一个小 commit 回滚；
5. 不改变未声明的产品行为、数据库格式或数据语义。

### 1.3 先保护不变量，再追求结构美观

重构的成功标准不是“目录看起来更漂亮”，而是：

- 既有功能行为不变；
- 数据不丢失；
- 图片不误删；
- 坐标和尺寸不漂移；
- 迁移可重复执行；
- 用户输入不被自动识别结果无条件覆盖。

## 2. 角色分工

### 2.1 Cursor：主实现者

Cursor 适合承担：

- 按阶段持续修改多个相关文件；
- 拆分 Flutter 页面和局部 Widget；
- 实现 Controller、State、Use Case、Codec；
- 运行 `dart format`、`flutter analyze`、`flutter test`；
- 根据编译错误快速修复；
- 做局部 UI 和交互调整；
- 在一个完整任务范围内更新实现和测试。

Cursor 实现时必须遵守：

- 只完成当前阶段；
- 不主动扩大范围；
- 不顺便重命名全仓库文件；
- 不修改生成文件，除非该修改由生成命令产生；
- 不在没有迁移计划的情况下修改数据库表结构；
- 完成后提供修改文件清单、验证命令和未完成事项。

### 2.2 Codex：架构顾问和审查者

Codex 适合承担：

- 把本次需求拆成可执行任务，不重开 `plan/plan_v1.10.md` 的四个阶段；
- 在 Cursor 修改前确定范围和验收标准；
- 审查 `git diff`；
- 检查跨模块一致性和数据生命周期；
- 识别数据库迁移、图片删除、坐标转换和状态同步风险；
- 设计和补充纯逻辑测试；
- 对明确的审查问题实施小范围修复；
- 产品行为有变化时更新 `plan/version_outline.md` 和 `docs/current-state.md`。

Codex 审查时默认只读，不要看到问题就直接重写整个模块。需要修改时，应先列出问题，再执行一个明确的修复任务。

## 3. 标准工作流

```text
读取 docs/current-state.md 和 docs/invariants.md
        ↓
Codex 定义本次任务、范围、不变量、验收标准
        ↓
Cursor 实现一个小的垂直切片
        ↓
Cursor 本地格式化、分析、测试
        ↓
Codex 只读审查 diff 和相关文件
        ↓
Cursor 或 Codex 定向修复审查问题
        ↓
形成一个小而明确的 Git commit
        ↓
若产品行为有变，记入 plan/version_outline.md
```

### 3.1 开始任务前

先执行：

```powershell
git status --short
git diff --stat
git branch --show-current
```

确认：

- 是否存在 Cursor 尚未提交的修改；
- 当前是否处于正确分支；
- 是否有其他未完成任务；
- 本次任务是否会触碰已有未提交文件。

如果工作区已有修改，不要直接 reset、clean 或覆盖。先确认这些修改是否属于当前任务。

### 3.2 定义任务边界

每个任务必须写清楚：

```md
### 任务标题

目标：

修改范围：
- ...

允许新增：
- ...

明确不修改：
- 数据库 schema
- 路由
- ONNX 模型接口
- 其他阶段负责的页面

必须保持：
- ...

验收标准：
- ...

相关测试：
- ...
```

### 3.3 Cursor 实现后

代码任务按约定执行下列检查；格式化只覆盖本次修改范围，以下尖括号内容须替换为实际路径，不能原样运行：

```powershell
dart format <本次修改的Dart文件或目录>
flutter analyze
flutter test
```

如果本次只修改纯 Dart 逻辑，也可以先运行相关测试，再运行完整测试。若某个命令无法运行，必须记录：

- 命令；
- 失败原因；
- 是代码错误、环境错误还是工具错误；
- 是否已经进行替代验证。

### 3.4 Codex 审查后

审查结果分三级：

- **必须修复**：会破坏功能、数据、迁移、坐标、文件生命周期或安全边界的问题。
- **建议修复**：明显的重复、可维护性问题或测试缺口，但不会立即破坏行为。
- **可以暂缓**：与当前任务无关、需要单独设计或风险较低的问题。

只有“必须修复”清空且验收标准满足后，任务才可以标记为完成。纯文档任务可以只做静态检查；用户明确要求不运行测试时必须遵守，并在记录中注明“未运行”，不能写成“通过”。

## 4. 文件并发和修改锁

### 4.1 不要同时修改同一个高风险文件

以下文件是共享锚点，任何时候只允许一个工具作为主修改者：

```text
lib/core/db/app_database.dart
lib/core/db/app_database.g.dart
lib/core/storage/image_store.dart
lib/core/vision/cutout/garment_pipeline.dart
lib/core/vision/cutout/contain_map.dart
lib/core/vision/onnx/onnx_runtime.dart
lib/core/vision/ocr/tag_ocr.dart
lib/widgets/piece_collage.dart
lib/features/wardrobe/item_edit_page.dart
lib/features/outfits/outfit_edit_page.dart
```

推荐方式：

```text
Cursor 正在修改 outfit_edit_page.dart
        ↓
Codex 只读审查，不写同一个文件
        ↓
Cursor 完成并提交
        ↓
Codex 如需修复，再单独修改并提交
```

### 4.2 分离写入范围

可以并行工作的任务必须有不重叠的写入范围。例如：

- 一个任务修改 `outfit` domain 和测试；
- 另一个任务修改 `calendar` 文档；
- 不能两个任务都修改 `outfit_edit_page.dart`。

如果两个任务最终必须修改同一个共享锚点，应串行执行。

### 4.3 不要覆盖未知修改

禁止使用以下方式“解决冲突”：

```powershell
git reset --hard
git clean -fd
```

除非用户明确要求并且已经确认目标范围。默认使用局部 diff、局部回退和小范围手工合并。

## 5. 本仓库必须保持的不变量

权威说明在 [docs/invariants.md](../docs/invariants.md)。下面是审查时仍要核对的条目：图片角色、路径、坐标、拼图、封面、OCR，以及 schema 1–9。这些规则优先级高于重构便利性。Cursor 每次处理相关模块时，都应将对应规则写入任务提示中。

### 5.1 衣物图片角色

- `garment` 图片可以作为衣物封面和穿搭素材。
- `tag` 图片只能用于吊牌识别和详情展示。
- `tag` 图片不能成为衣物主图。
- `tag` 图片不能参与穿搭拼图。
- 没有 processed cutout 时，衣物照可以回退到原图；吊牌照不能作为该回退图。

相关锚点：

```text
lib/features/wardrobe/photo_role.dart
lib/features/wardrobe/data/item_repository.dart
lib/widgets/piece_collage.dart
lib/features/outfits/providers.dart
```

### 5.2 图片路径和文件生命周期

- 数据库保存路径，实际文件由 `ImageStore` 管理。
- 只能删除 `ImageStore` 自己拥有的文件。
- 不能删除用户原始路径上的文件。
- 替换衣物图片时，要清理不再使用的 original、processed、mask 文件。
- 删除衣物时，要清理该衣物关联的图片文件和数据库记录。
- 删除或替换失败时，不能无条件删除仍被数据库引用的文件。
- 数据库事务和文件系统操作不是同一个原子事务，重构时必须明确失败回滚和孤立文件清理策略。

相关锚点：

```text
lib/core/storage/image_store.dart
lib/features/wardrobe/data/item_repository.dart
lib/features/outfits/data/outfit_repository.dart
```

### 5.3 图片坐标系统

项目中必须区分：

1. 原图或处理图像素坐标；
2. Mask 像素坐标；
3. Flutter Widget 本地坐标；
4. 拼图画布归一化坐标。

禁止在不同 Overlay 中各自编写近似的坐标换算。点击、擦除、填补、Mask 预览和区域框选必须依赖同一个坐标转换锚点。

共享锚点是 `lib/core/vision/coordinates/image_coordinate_mapper.dart`。点选、擦除、填补和拼图命中都走它，不要在各 Overlay 里再写一套换算。

### 5.4 拼图布局

- 拼图画布比例保持 `3:4`。
- `CollagePlacement` 的 `x/y/w/h` 必须使用统一的归一化语义。
- 布局保存、加载、合并、命中测试和绘制必须使用同一套单位。
- `z` 或等价字段必须保持稳定的层级顺序。
- 关联衣物被移除后，布局应丢弃对应项目。
- 新关联衣物应得到稳定的默认位置。
- 空布局字符串表示用户删除过拼图，不能随意等同于“从未初始化”。
- 非法或旧版 JSON 必须安全回退，不能让列表页或详情页崩溃。

相关锚点：

```text
lib/widgets/piece_collage.dart
lib/features/outfits/outfit_collage_board.dart
lib/features/outfits/providers.dart
```

### 5.5 穿搭封面策略

封面策略只能有一个权威实现，不能在列表、详情、日历分别复制一套判断。

需要覆盖：

| 全身照 | 拼图 | coverMode | 预期 |
|---|---|---|---|
| 有 | 有 | `photo` | 使用全身照 |
| 有 | 有 | `collage` | 使用拼图 |
| 有 | 无 | `collage` | 回退全身照 |
| 无 | 有 | `photo` | 回退拼图 |
| 无 | 无 | 任意 | 空状态 |

删除其中一种封面后，剩余封面必须能正确接管显示。

### 5.6 用户输入和自动识别

- OCR 和颜色分析只能填充空字段或提供建议。
- 不能无条件覆盖用户已经填写的字段。
- OCR 原文和解析结果要分开保存。
- 识别失败时仍然允许用户手动保存衣物。
- 模型不可用不能阻塞基础的手动录入流程。

### 5.7 数据库迁移

- 已发布的 schema 1–9 不重写。
- 新增数据库字段或表必须增加 `schemaVersion`。
- schema 9 是现有快照基线；未来高于 9 的升级按项目约定生成并实现新的迁移步骤。不要仅增加 schemaVersion 而遗漏迁移实现。
- 迁移前检查表和列是否已存在的逻辑不能被随意删除。
- 新迁移必须有旧库升级、新库创建、再次打开不重复迁移的测试；手写幂等辅助逻辑另外验证重复调用。未来计划与已实现的迁移步骤要明确区分。
- 不直接手改 `lib/core/database/app_database.g.dart`。
- 生成文件由工具生成，源文件修改后再运行生成命令。

相关锚点：

```text
lib/core/database/app_database.dart
build.yaml
drift_schemas/
test/db_migration_test.dart
```

### 5.8 本地优先边界

当前产品不接：

- 云同步；
- 真实天气接口；
- Python OCR 服务；
- 在线抠图服务；
- 远程模型服务。

重构不能无意间引入网络依赖或改变数据存储位置。

## 6. 如何使用工程计划

`plan/plan_v1.10.md` 的四个阶段已经完成。新任务按第 3 节小步做，不再重开那四个阶段，也不另设一套阶段编号。

### 6.1 新任务怎么开始

1. 先读 [docs/current-state.md](../docs/current-state.md) 和 [docs/invariants.md](../docs/invariants.md)，确认这次改动不改变未声明的产品行为。
2. 用第 7 节模板写清目标、允许修改的文件和验收命令。
3. Cursor 实现，Codex 对固定 diff 做只读审查。审查期间不要继续改同一批文件。
4. 优先处理数据丢失、误删文件、迁移、坐标错位和异步竞态，然后处理目录和命名。

### 6.2 每阶段的任务交接记录

可将以下记录放在主计划当前阶段下面，或作为双方的交接消息：

```md
任务 ID / 主计划章节：
状态：未开始 / 进行中 / 待审查 / 已完成 / 阻塞
主修改者：Cursor 或 Codex
基线提交：
审查目标：工作区 diff 或明确的提交范围
目标与验收标准：
允许修改的文件：
明确不修改：
必须保持的行为和数据格式：
实际修改文件：
验证命令与结果：通过 / 失败 / 未运行（原因）
未解决问题：
下一位执行者与下一步：
```

任务记录中不要放用户照片、吊牌原文或本机数据库内容；测试优先使用合成数据、临时目录和专门的测试库。

### 6.3 结构建议不是强制新增组件

- 仓库已经存在 `ContainLayout`、拼图归一化布局、OCR/颜色结果的序列化代码和编辑会话状态；先核实，再决定移动、复用或补测试。
- 不为了遵循目录示例而重复创建 Mapper、Codec、Controller 或 Use Case。
- 模型和 Codec 优先归属使用它的功能模块，只有真正跨功能复用的内容才放入 `core`。
- Controller 管理业务状态；焦点、滚动、输入框、局部手势等 UI 状态可以继续由 Widget 管理。
- 异步处理需验证：切换图片、退出页面或连续发起请求后，旧结果不能覆盖当前会话；优先明确任务 ID、取消和资源生命周期，再讨论后台计算优化。
- 纯重构默认保持数据库 schema、JSON 格式和路由不变；行为修复与格式迁移另列任务。

### 6.4 文件保存策略的安全约束

不要将“数据库提交成功，再把图片移动到最终路径”当成完整事务方案：移动失败会留下数据库引用缺失文件。

具体方案必须单独设计和测试，至少满足：

1. 先准备本次新增文件，并确保数据库将引用的最终路径可用；
2. 再提交数据库引用；
3. 数据库失败时，仅清理本次新建且未被引用的文件，不删除历史文件；
4. 数据库提交后，再清理已经没有引用的旧文件；清理失败应能重试，不应把已成功保存误报为整体失败；
5. 崩溃恢复需要额外的操作记录或保守的孤立文件扫描，普通 try/catch 不提供跨文件系统和数据库的原子性。

这只是验收约束，不授权立即改造 ImageStore。具体实施顺序仍以主计划和当前任务为准。

## 7. Cursor 提示词模板

### 7.1 实现任务模板

```text
请只完成下面这一项任务，不要重开 plan/plan_v1.10.md 的四个阶段。

目标：
- ...

允许修改：
- ...

允许新增：
- ...

不要修改：
- 数据库 schema
- 路由
- 视觉模型接口
- 本阶段以外的页面

必须保持：
- tag 图片不能作为衣物封面或拼图素材
- 用户已有字段不能被 OCR 覆盖
- 图片坐标继续遵守统一映射
- 不改变现有数据格式和路由

完成后：
1. 运行 dart format
2. 运行 flutter analyze
3. 运行相关 flutter test
4. 列出修改文件
5. 列出测试结果
6. 列出仍未完成的事项
```

### 7.2 只修复编译问题模板

```text
请只修复当前编译/分析错误，不进行额外重构。

约束：
- 保持当前 API 和数据格式；
- 不修改数据库 schema；
- 不改变 UI 行为；
- 不重命名无关文件；
- 修复后列出每个错误对应的修改。
```

### 7.3 任务完成前的自审模板

```text
请对刚完成的任务做一次只读自审：

1. 是否超出了任务文件范围？
2. 是否复制了已有业务规则？
3. 是否破坏图片角色、封面、坐标或迁移不变量？
4. 是否可能误删用户文件？
5. 是否遗漏了空值、非法 JSON、重复关系或失败回滚？
6. 是否需要增加纯逻辑测试？

不要直接扩大重构范围，只列出问题及优先级。
```

## 8. Codex 审查提示词模板

```text
请只审查当前工作区和当前任务 diff，不要主动进行大规模重构。

任务目标：
- ...

重点检查：
1. 是否超出本次任务范围；
2. 是否破坏现有产品行为；
3. 是否破坏数据库迁移兼容性；
4. 是否存在图片误删、泄漏或孤立文件风险；
5. 是否混用了界面坐标、图片像素坐标和拼图归一化坐标；
6. 是否让 OCR 覆盖用户字段；
7. 是否把 tag 图片当成主图或拼图素材；
8. 是否复制了封面、主图或回退策略；
9. 是否缺少边界测试；
10. 是否有明显的资源释放、异步生命周期或 BuildContext 风险。

请按以下格式输出：

必须修复：
- 文件、问题、原因、建议

建议修复：
- 文件、问题、建议

可以暂缓：
- 问题、理由

建议新增测试：
- 测试文件和场景
```

## 9. Git 提交规范

### 9.1 提交前检查

```powershell
git status --short
git diff --check
git diff --stat
```

然后按任务运行：

```powershell
dart format <本次修改的Dart文件或目录>
flutter analyze
flutter test
```

### 9.2 提交粒度

一个 commit 应该描述一个完整的小变更，例如：

```text
refactor: extract outfit cover policy
test: add collage layout codec cases
refactor: introduce image coordinate mapper
fix: preserve user fields during OCR autofill
refactor: split item edit photo step
test: cover image store rollback behavior
docs: update refactor workflow
```

不要把以下无关内容混入功能 commit：

- 自动生成的 build 产物；
- `.dart_tool`；
- 发行压缩包；
- 与当前任务无关的格式化；
- 顺手修改的历史计划文档。

### 9.3 计划状态更新

每个阶段至少使用以下状态之一：

```text
未开始
进行中
待审查
已完成
阻塞
```

只有满足以下条件，才能标记为“已完成”：

- 实现范围完成；
- 相关测试完成；
- `flutter analyze` 没有新增问题；
- Codex 或另一位审查者完成审查；
- 未解决的“必须修复”问题为零；
- 计划文件已经更新。

## 10. 高风险场景处理

### 10.1 Cursor 大范围修改后

如果 Cursor 一次修改很多文件：

1. 不要立即继续叠加新任务；
2. 先看 `git diff --stat`；
3. 按目录检查 diff；
4. 将修改按“目标相关 / 顺手修改 / 未知修改”分类；
5. 必要时拆分 commit；
6. 先修复边界和数据风险，再处理风格问题。

### 10.2 测试失败但原因不明确

先判断属于：

- 编译错误；
- 逻辑回归；
- 数据库迁移失败；
- ONNX/Windows 环境问题；
- 文件权限或路径问题；
- 测试夹具问题。

不要因为环境测试失败就修改业务代码，也不要因为业务测试失败就简单增加 timeout 或 ignore。

### 10.3 需要修改数据库 schema 时

必须单独开一个任务：

1. 说明新增或修改的表/列；
2. 增加 schemaVersion；
3. 生成 Drift migration；
4. 检查生成步骤；
5. 增加旧库升级测试；
6. 增加新库创建测试；
7. 确认旧数据和路径仍然存在；
8. 再修改 UI 和 Repository。

数据库 schema 任务不要和大型 UI 重构混在同一个 commit。

### 10.4 需要修改坐标系统时

必须先写出单位表：

| 名称 | 单位 | 原点 | 范围 | 使用位置 |
|---|---|---|---|---|
| ViewportPoint | Flutter 本地像素 | Widget 左上角 | 由布局决定 | 手势层 |
| ImagePixelPoint | 图片像素 | 原图左上角 | 图片宽高 | Mask/模型 |
| CollagePoint | 归一化比例 | 画布左上角 | 通常 0..1 | 拼图布局 |

在转换逻辑统一前，不要让各页面分别调整缩放倍率或偏移量。

## 11. 完成定义（Definition of Done）

一个重构任务只有同时满足以下条件，才算完成：

- [ ] 目标和文件范围与计划一致；
- [ ] 没有无关的大规模改动；
- [ ] 产品行为和数据语义保持不变，除非计划明确要求改变；
- [ ] 图片角色和图片文件所有权规则保持不变；
- [ ] 坐标单位和转换边界保持一致；
- [ ] 数据库 schema 和迁移策略没有被绕过；
- [ ] 相关测试已经补齐，或记录本任务不适用的原因；
- [ ] 修改过的 Dart 文件已格式化，或标记不适用；
- [ ] `flutter analyze` 已执行并记录结果，或说明未运行/不适用；
- [ ] 相关测试已执行并记录结果，或说明未运行/不适用；不得把未运行记为通过；
- [ ] Codex 或另一位审查者已经检查 diff；
- [ ] “必须修复”问题为零；
- [ ] Git commit 信息能说明这次变更；
- [ ] 若产品行为有变，已记入 `plan/version_outline.md`；否则说明本次不涉及产品范围。
